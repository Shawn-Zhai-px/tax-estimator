# 税务估算工具 — 场景覆盖与产品化分析

> 本文档对应 `MyPlan.md` 中"讨论以及计划过程"部分的 5 个问题。按照该文件的要求，
> 本文档**只做分析，不涉及任何代码或文件层面的修改**。写作时间：2026-08-21。

---

## 1. 现有税务估算功能，能否准确覆盖典型加州居民的各类场景？

### 结论先行

**不能完全覆盖。** 当前 `estimateTax()`（`src/lib/calculateTax.ts`）能较好地处理
**"单一 W-2 工资收入 + 使用标准扣除 + 无抚养人"** 这一种最基础的场景。一旦涉及
自雇/灵活就业、房产相关扣除、抚养人抵免、学生贷款利息等，估算结果会明显偏离真实
税负（通常是**低估**了自雇者的税负、**高估**了有房贷/子女家庭的税负，因为这些抵扣
和抵免根本没有被计算在内）。

### 现有能力盘点

| 维度 | 现状 |
|---|---|
| 联邦税 | 按 4 种报税身份（Single/MFJ/HoH/MFS）套用累进税率表 + 标准扣除（或用户手动输入的一个"总额"itemized 数字） |
| 加州税 | 累进税率表 + CA 标准扣除 + Mental/Behavioral Health Services Tax（应税收入超 $1M 部分 +1%） |
| 德州 | 无州税 |
| 工资代扣（另一个页面 `/paycheck-withholding`） | 联邦 W-4 代扣、CA DE-4 代扣、FICA（社保+Medicare+Additional Medicare）、401(k)/Roth catch-up/dependent care FSA 年度封顶、单次 bonus |

### 按用户群体逐一核对

- **普通 W-2 上班族、无房、无子女、用标准扣除**：✅ 基本准确。这是工具设计的核心场景。
- **自雇 / 自由职业 / 灵活就业（1099 收入）**：❌ **明显缺失**。完全没有计算：
  - **自雇税（SE Tax）**：净自雇收入 × 92.35% × 15.3%（其中 12.4% 社保部分有工资基数上限，
    2.9% Medicare 无上限），这往往是自雇者税负里除所得税外最大的一块。
  - 自雇税可抵扣一半作为联邦"调整项"（Schedule 1）。
  - **QBI 扣除**（Section 199A，合格营业收入 20% 扣除，有收入门槛/行业限制）。
  - 自雇者可全额抵扣的健康保险保费。
- **有一套自住房**：⚠️ **部分缺失**。房贷利息、房产税（SALT，联邦有上限）目前
  只能由用户自己算好后，作为一个笼统的"itemized deduction 总额"手动输入 —— 工具本身
  不帮用户拆解、也不会告诉用户这个总额是否划算（vs. 标准扣除）。且 CA 州这一侧
  **完全没有实现"CA 自己的分项扣除"**（CA 有独立的 Schedule CA (540)，不跟随联邦
  SALT 上限规则），目前 CA 永远用标准扣除。
- **不同婚姻状况（未婚/已婚/离婚/丧偶）**：✅ 基本覆盖。未婚→Single，已婚→MFJ/MFS，
  离婚后通常→Single 或（有抚养子女时）HoH。⚠️ 小缺口：**丧偶者的 Qualifying
  Surviving Spouse（QSS）身份**未单独建模（QSS 在配偶去世后 2 年内可按 MFJ 税表
  计税，目前只能选 Single/HoH，多缴税）。
- **不同子女情况（无/一个/多个/已成年）**：❌ **明显缺失**。没有计算：
  - **Child Tax Credit**（每个符合条件子女 $2,000，有收入 phase-out）。
  - **Credit for Other Dependents**（每个其他抚养人 $500，含已成年但仍被抚养的子女）。
  - **Dependent Care Credit**（与另一页面的 Dependent Care FSA 输入没有联动）。
  - **EITC**（低收入家庭，尤其"灵活就业/时薪"人群相关性较高）。
  - 报税身份的 HoH 选项本身已部分反映"有抚养人"，但具体抵免金额完全没算。
- **一两辆代步车**：➖ 对普通 W-2 家庭通常不涉及税务；仅在以下情况相关，且都未建模：
  自雇者的商业里程扣除、购买符合资格的电动车享受 Clean Vehicle Credit。
- **不同贷款情况**：
  - 房贷利息 → 见上文"有房"部分（未拆解，仅能塞进 itemized 总额）。
  - **学生贷款利息扣除**（最高 $2,500，按 MAGI phase-out，属于联邦"调整项"而非
    itemized）：❌ **完全缺失**，且这是一个很多年轻上班族/自由职业者都用得上的扣除。
  - 车贷利息：个人车贷利息本身**不可抵扣**（除非自雇者的商业用途部分），所以这里
    不算功能缺口。
- **不同社保缴纳情况（公司+个人 vs 全部自己缴）**："公司+个人分摊"就是普通 W-2 的
  FICA 代扣，`/paycheck-withholding` 页面已经模拟得比较完整；"全部自己缴"对应的正是
  自雇税，回到上面自雇税缺口。

### 分优先级的修复方案

**Phase A（性价比最高，建议优先做）**
1. 自雇税计算：新增"自雇净收入"输入项，按 92.35% × 15.3%（社保部分套用
   `/paycheck-withholding` 页面里已有的 `SS_WAGE_BASE` 常量做封顶）算出 SE Tax，
   并把其中一半计入联邦"调整项"降低 AGI。
2. Child Tax Credit / Credit for Other Dependents：新增"抚养人数量 + 类型（子女/其他）"
   输入，按官方金额和 phase-out 公式计算抵免，从联邦应缴税额里扣减。
3. 学生贷款利息扣除：新增一个金额输入框 + MAGI phase-out 计算，直接减少联邦应税收入。

**Phase B（中等工作量）**
4. Itemized deduction 拆解 UI：房贷利息 + SALT（房产税+州税，联邦有上限）+ 慈善捐赠 +
   超过门槛的医疗费用，自动加总并和标准扣除比较，替代现在"直接输入一个总额"的做法。
5. CA 自己的分项扣除（Schedule CA (540) 简化版），让 CA 侧不再永远只能用标准扣除。
6. Dependent Care Credit，并与已有的 Dependent Care FSA 输入做联动（不能同时对同一笔
   支出既走 FSA 免税又拿信用）。

**Phase C（优先级较低 / 复杂度较高）**
7. QBI（Section 199A）扣除。
8. 资本利得/合格股息的优惠税率。
9. AMT、Net Investment Income Tax（3.8%，注意这和已实现的 Additional Medicare 0.9%
   是两个不同的税种）。
10. HSA、传统 401(k)/IRA 供款对 AGI 的调整。
11. EITC。

## 2. 移动端适配：能否区分桌面/移动浏览器？工作量大不大？要不要付费？

**现状**：项目已经在用 Tailwind CSS，这本身就是响应式方案（`sm:`/`lg:` 断点已经在用），
不需要额外付费或引入新框架。

两条可选路径：

| 方案 | 说明 | 工作量 | 费用 |
|---|---|---|---|
| **响应式 CSS（推荐）** | 继续用 Tailwind 断点让同一套页面在不同屏幕宽度下自适应布局（窄屏单列、宽表格横向滚动等，`AnnualScheduleTable` 里已经用了这个模式） | 低～中，主要是逐页面测试 + 微调 class，不需要新技术栈 | 免费 |
| **User-Agent 设备识别** | 用 Next.js 自带的 `userAgent()`（`next/server`）或 `react-device-detect` 库判断桌面/移动，分别渲染不同布局甚至不同组件 | 中～高，要维护两套 UI 逻辑，通常只有"移动端要完全不同交互形态"（比如原生 App 感的界面）才值得做 | 免费（库本身免费，付出的是开发时间） |

**建议**：优先把响应式 CSS 做扎实（这也是当前架构的自然延伸，成本最低），不需要单独
做设备识别。如果想让手机用户"像个 App 一样"使用，成本很低的加分项是加一个
`manifest.json` + Service Worker 做成 PWA（可"添加到主屏幕"），同样免费、工作量不大。

## 3. 登录模块该怎么设计？自研 vs 第三方，要不要付费？

**建议：不要自研，用现成的第三方方案。** 密码存储、会话管理、邮箱验证、找回密码、
第三方登录（Google/Apple 等）这些环节涉及大量安全细节，对于这种规模的项目自己写
风险收益比很差。

| 方案 | 特点 | 费用 |
|---|---|---|
| **Auth.js（原 NextAuth.js）** | 开源库，自己部署；纯 OAuth 登录可以不需要数据库（无状态 JWT），要做角色/会话持久化则仍需接一个数据库 | 免费（自建服务器成本） |
| **Clerk** | 托管服务，React 组件开箱即用，UI/MFA/社交登录/会话全包，接入速度最快 | 有免费额度，超出后按月活用户数（MAU）计费 |
| **Supabase Auth** | 和 Supabase 的 Postgres 数据库是一整套，登录+数据库一起搞定 | 免费额度较慷慨，超出后阶梯计费 |
| **Firebase Auth** | Google 生态，免费额度大，文档成熟 | 同上，免费额度用完后计费 |

（具体免费额度/价格会随时间调整，落地前建议直接查各家官网最新定价。）

**推荐**：如果第 5 点也打算引入数据库，**Supabase**（Auth + Postgres 一体）性价比最高，
一次接入两件事都解决了；如果暂时不想碰数据库、只想尽快加个登录，**Clerk** 接入最快。
不建议自己从零写登录系统。

## 4. 如何防止恶意高频连接/攻击？

分两层看：

- **托管平台层面（免费/低成本，优先做）**：如果部署在 Vercel，其边缘网络自带一定的
  DDoS 缓解；在前面加一层 **Cloudflare（免费版即可）**能获得 WAF、基础限流、
  Bot 识别等能力，性价比很高，几乎是当前这种"全静态/纯前端计算"网站的标配。
- **应用层限流（等到有后端接口/登录之后再做）**：目前这个项目所有计算都在浏览器端
  完成，没有任何服务器 API、没有数据库、没有表单提交到后端 —— 攻击面本身很小。
  等到未来加了登录、付费功能、或任何 API 路由之后，再引入 **Upstash Ratelimit +
  Vercel Edge Middleware**（Upstash 有免费额度，配合 Vercel Edge Middleware 做
  按 IP/按用户的限流），是当前生态里最简单好用的组合。

**建议**：现阶段先上 Cloudflare 免费版即可覆盖大部分场景；等真正有了服务端交互
（登录、数据库写入）再补应用层限流，不需要现在就投入。

## 5. 是否需要数据库？第三方登录/付费模块的数据怎么共享？

**现状**：目前项目 0 后端、0 数据库、纯前端计算，不收集任何用户信息——这也是
`MyPlan.md` 第 4 条明确要求的（税表展示"只涉及数字，不涉及用户信息收集"）。

**一旦加上登录 + 未来的付费功能，就需要一个数据库**，但不代表要"从零建库"：

- 如果用 Clerk/Auth0 这类第三方登录服务，**用户账号本身**（邮箱、密码哈希、
  会话）由它们托管，你不需要自己存这些敏感信息。
- 但你大概率仍然需要**自己的一个小数据库**，用来存"跟你产品相关"的数据 ——
  比如：用户保存的历史估算记录、订阅/付费状态缓存、偏好设置——这些数据用
  第三方登录服务给你的 **user ID 作为外键**关联即可，是非常标准的"借用第三方登录、
  自建业务数据库"模式，不需要重复存储对方已经管理的敏感信息。
- **数据同步**：通常通过 **Webhook** 完成 —— 比如 Clerk 在用户注册/资料变更时、
  Stripe 在订阅状态变化时，各自向你的一个 API 路由推送事件，你的后端把需要的
  字段写入自己的数据库即可，不需要什么特殊的"数据共享"机制。

**推荐组合**：**Supabase**（Postgres 数据库 + Auth 一起）最省事；或者 **Vercel
Postgres / Neon（数据库）+ Clerk（登录）+ Stripe（付费，如果需要）** 的组合，
三者都是这个规模项目里成熟、有免费额度、可以直接抄作业接入的成熟组件，
不建议自己实现登录或支付相关的存储逻辑。

## 小结

| 问题 | 一句话结论 |
|---|---|
| 1. 场景覆盖 | 目前只准确覆盖"W-2 + 标准扣除 + 无抚养人"的最简单场景，自雇税、房贷/房产税分项扣除、子女相关抵免、学生贷款利息是最值得优先补的四块 |
| 2. 移动端 | 继续吃 Tailwind 响应式的老本即可，不需要单独做设备识别，免费 |
| 3. 登录 | 别自研，Supabase Auth 或 Clerk 二选一，都有免费额度 |
| 4. 防攻击 | 现阶段 Cloudflare 免费版足够，等有后端接口后再加 Upstash 限流 |
| 5. 数据库 | 加登录/付费后需要，但只存自己的业务数据，用户账号交给第三方登录服务托管，Supabase 一体化最省事 |
